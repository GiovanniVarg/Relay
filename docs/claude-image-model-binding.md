# Claude image model binding

Image-bearing requests on the existing `sonnet`, `opus`, and `haiku` logical selections pin `--model` to `claude-sonnet-5-5`, `claude-opus-5-5`, and `claude-haiku-5-5`, respectively. Text-only requests retain the rotating aliases. This adds no model selections, billing approvals, authentication calls, or automatic fallback.

`shared/claude-image-contract.ts` owns the finite mapping and `claude-image-pin/v1` contract. Claude catalog entries expose the concrete image binding, a human-readable description, and official-model-docs modality evidence. Bounded model summaries retain the binding. The capability resolver accepts this docs-based evidence only for an exact mapped alias, exact binding and contract, and the expected text/image modalities; arbitrary family names or docs-source labels are insufficient. Existing provider-catalog evidence handling is unchanged.

The Chat, Work, and Agent transports share the pin. Image response validation checks every reported top-level assistant model and system init model, plus the native initialize model when present. A contradictory primary model fails immediately. Init and control initialize reports validate selection only; they do not prove which model produced the response. Without an exact top-level assistant response witness, successful results require exactly one reported modelUsage key equal to the pin. With an exact assistant response witness, aggregate usage may also contain auxiliary native-worker models. Native events with parent_tool_use_id remain excluded from primary evidence. Model validation precedes terminal response text emission and success acceptance. Logical actualModel stays the approved alias for routing identity.

This contract verifies the requested transport model and accepted CLI evidence, not the provider's internal execution. If the CLI, managed policy, or account cannot use the exact model, the request fails; no alias or family fallback is accepted. Installed Claude Code 2.1.322 was independently checked before this change; the implementation does not add version probes or require undocumented initialize fields.

Response evidence resets before the first assistant, stream, or result event after each native terminal result. A previous response cannot authorize missing or ambiguous model reports in a continuation. The documented streaming `message_start.message` is a primary assistant Message: its model is checked before text deltas and, when its role is assistant and its model is exact, supplies response evidence. Init remains selection evidence only. Documented `fallback` content blocks and `usage.iterations` entries of type `fallback_message` fail closed on primary streams/messages/results. Native nested events remain filtered first; auxiliary aggregate `modelUsage` keys remain distinct from these explicit primary fallback signals.

Primary references reviewed 2026-11-11: [Claude Code model configuration](https://code.claude.com/docs/en/model-config) documents full model-name selection and rotating aliases; [Claude models overview](https://platform.claude.com/docs/en/models/overview) documents the three exact IDs and image input. Re-review the contract before changing pins.

Streaming boundaries and fallback shapes were checked against [Streaming messages](https://platform.claude.com/docs/en/build-with-claude/streaming) and [Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback). These document the assistant Message in `message_start`, fallback block boundaries, and serving-model fallback usage; no additional event names are assumed.

Verification uses synthetic process fixtures: actual adapter catalog to capability resolution; bounded catalog metadata; all three aliases across Chat, Work, and Agent with exact image bytes and CLI arguments; wrong, missing, mixed, and contradictory primary evidence; auxiliary native-worker usage; and existing text-provider suites. No live inference was used.
