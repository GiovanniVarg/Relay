Current Agent workflow: requested checks run without repeated approval prompts. `relay_apply_change` displays an inline summary of the exact checked revision and waits for approve or no in chat, then queues an approved revision until the requesting turn and all other active work finish. Essential questions can be answered in chat. The optional editor retains its manual review controls. See [conversational Agent behavior](../README.md#conversational-agents).

# Editing the harness from inside Relay

The Change Relay workspace provides source browsing/editing, optimistic file saves, additions and deletions, before/after review, revision-bound checks, an isolated frontend preview and explicit activation. Every supported Agent subscription receives the same source-editing app tools. Ask a bot, for example: “Make the sidebar more compact. Create a Relay change, inspect the diff, run checks and apply it when ready.”

Source includes server, client, shared code, scripts, tests, docs and root build/launcher configuration. Each draft is a real independent copy under the detected user's Relay-workspaces directory. Runtime data, node_modules, dist, hidden/private files and non-text payloads are excluded. A file is limited to 200,000 bytes, a draft to 20,000,000 bytes and 5,000 source files. Dependencies and compiled files are generated separately for checks and activation.

Checks use fixed TypeScript, Vite and test commands, sanitize inherited environment variables and use an independent dependency tree. Changed package manifests require a locked npm ci with lifecycle scripts disabled. Native dependencies requiring install scripts may need manual setup. Checks execute draft code as the current OS user: source separation is not an OS sandbox or a substitute for reviewing code. A prompt alone cannot enforce a security boundary. Native tools with local shell access retain the authority granted by their runtime.

Checks and activation requests bind an exact source revision. Saving files invalidates readiness. Changes to checked source, build or dependencies invalidate the deployment manifest. A changed running installation requires a new draft based on the current version. Frontend preview uses a separate local origin, synthetic disconnected accounts and inert APIs; backend behavior is tested through checks and startup verification.

Apply requires idle direct/group/delegated work, no unresolved native execution exclusions, and no active build/test jobs. It blocks new API mutations, tasks, Telegram work and provider dispatch until verification completes. The current server stays alive until a trusted copy of the installed updater acknowledges candidate preflight. That updater waits for graceful shutdown, creates a consistent SQLite backup and recoverable source/dependency backup, installs exactly the checked manifests and starts Relay with a nonce and startup hold. Health and unchanged existing saved records are verified before releasing work. Only the updater's own candidate child can be terminated for failed-start recovery.

Update status survives restart in .relay-data/self-update/jobs. Successful backups are in .relay-data/self-update/backups, with source beneath app and the consistent database separately. Revert creates a source draft against the current app while preserving current conversations; it needs the normal checks and review. A failed activation retains candidate files/database as evidence and restores the previous version. An OS crash or power loss that kills the updater itself can require manual recovery from its backup and movement journal; automatic recovery covers a running updater's detected startup failure. Never delete recovery files while diagnosing an interrupted update.

The apply tool is advertised to bots, but it requires a separate internal human confirmation that routine Agent automatic approvals cannot satisfy. Its bounded title, revision, check status and changed filenames are saved in chat; source content, logs and local workspace paths are omitted. Ambiguous replies keep waiting; denial, cancellation, expiry and stale revisions cannot queue activation. The local session/CSRF boundary and UI review protect the normal app flow, not against arbitrary code already running with the user's OS permissions. Checks and health verification make no live subscription inference calls.
